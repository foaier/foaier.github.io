“已经接了 MCP，为什么还需要 Skill？”可以拿做报销来理解：工具能查订单、读发票、提交申请；Skill 告诉助手这类任务应该按什么顺序做、参考哪些规则、遇到什么情况停下来。

一个偏向能力接口，一个偏向工作方法。它们可以组合，也可以独立使用。

## Skill 通常装了什么

一个文件式 Skill 通常是目录里的 `SKILL.md`，旁边可以放参考资料、脚本和模板。以工单归类为例：

```text
ticket-triage/
  SKILL.md
  references/
    categories.md
  assets/
    reply-template.md
```

`SKILL.md` 可以写成下面这样。这里只是教学文本，不会在博客里自动执行：

```markdown
---
name: ticket-triage
description: 根据既定类别整理客服工单，在归类与追问信息时使用。
---

先读取类别说明，再提取用户明确表达的问题。
信息不足时提出一个澄清问题，不猜测订单状态。
输出主类别、已知事实和缺少的信息。
如果需要查询业务数据，仅使用当前用户有权访问的只读工具。
```

描述要帮助系统判断什么时候使用它。把所有技能都描述成“帮助用户完成任何任务”，发现和选择就没有意义了。

## 为什么强调按需加载

把所有说明一次塞进系统提示词，会增加上下文开销，还可能引入互相冲突的规则。

Skill 通常先暴露名称和描述，任务匹配后再加载详细指令，必要时读取资料或运行脚本。这种逐步展开，让复杂业务说明不必每次都全部发送给模型。

但按需加载是机制，不是效果保证。技能描述含糊、资源过长，模型仍可能选错或漏读。需要用真实任务检查选择结果。

## 文件式、代码式、类式怎么选

| 形式 | 比较适合 | 主要代价 |
| --- | --- | --- |
| File-based | 文档、模板和规则更新较多 | 路径、发布、文件访问要管理 |
| Code-defined / Inline | 简短且随应用发布的说明 | 文本修改需要走代码发布流程 |
| Class-based | 需要封装逻辑或注入业务依赖 | 生命周期与测试更重要 |
| 多来源组合 | 同时使用通用规则和专属能力 | 同名冲突、过滤和版本要明确 |

当前 Agent Framework 文档分别提供文件源、内联和类式技能，以及组合来源的方式。不要照着旧示例猜类型名，先看对应语言和包版本。

组合以后要规定优先级，避免两个同名技能悄悄覆盖。可以把技能名、版本和来源记录在运行日志里，出问题时才知道模型看到的是哪份说明。

## 依赖注入解决的是对象管理

类式技能可能要用订单服务、配置、日志或 HTTP 客户端。通过 DI 传进来，比在技能内部到处创建这些对象更容易替换和测试。

但不能把带着请求身份的 scoped 服务，长期挂在全局 singleton 技能上。工具真正执行时，应当在正确的作用域里取得身份和业务依赖，并明确异步操作结束后如何释放资源。

下面是设计层面的关系，具体注册方式取决于采用的技能类型：

```text
请求作用域
  ├─ 已认证的用户身份
  ├─ 工单应用服务
  └─ 本次技能/工具执行

可共享配置
  ├─ 技能说明与版本
  └─ 不包含用户状态的客户端配置
```

## 脚本和说明不能获得额外权限

加载了一个 Skill，不等于它的脚本应该拥有整个文件系统和所有网络凭证。给运行器明确的工作目录、可访问资源、超时和输出限制。

文件中的指令也不能覆盖用户的当前要求或应用权限。来自外部来源的技能，先审查再使用；别把“这是技能要求”当成跳过业务授权的理由。

最后用同一组任务比较：不加载技能、加载单个技能、加载组合技能。观察分类正确性、工具调用、读取资料的数量和成本，才知道它究竟帮了什么。
