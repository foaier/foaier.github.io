知识库问答的演示通常很顺：上传文档，输入问题，几秒后得到一段答案。到了真实项目里，问题就来了：引用错页、拿到旧政策、表格切碎了，甚至用别人部门的资料回答。

RAG 可以先理解成“开卷作答”：把相关资料找出来，再交给模型回答。卷子找错了，后面的文笔再好也救不了。

## 把流程分成两条线

入库是一条相对慢的线，查询是一条要求及时响应的线。把它们分开，才容易定位问题。

```text
入库：原文 → 解析 → 清洗 → 分块 → 向量化 → 索引与权限
查询：问题 → 授权范围 → 检索 → 合并/重排 → 组织上下文 → 回答与引用
```

一篇文档更新后，不只是把新版本再传一遍。旧块可能需要删除，权限可能变化，引用地址也要保持可追溯。最好有文档 ID、版本、内容哈希和索引状态。

## 切块先按内容结构，再考虑长度

把每 500 个字符切一段很容易实现，但可能把“退款需要满足以下条件”和后面的条件列表切开。

可以先按标题、段落、列表、表格组织，再在过长时继续拆分。保留标题路径，让单独拿出来的片段仍然知道自己属于哪个主题。

重叠能减少边界丢失，也会增加重复召回和成本。没有一个适合所有文档的切块长度。拿几组真实问题比较命中效果，比照抄一个数字更可靠。

## 检索回来以后，别急着全部塞进去

关键词检索擅长产品型号、单号和专有词；向量检索擅长接近但不完全相同的表达。混合检索先扩大候选，再根据问题做重排，常比单一路径更稳。

重排不是无限增加资料。上下文有长度限制，重复、过期或互相矛盾的段落会干扰回答。应当去重，优先保留相关且版本明确的证据。

权限必须在资料交给模型之前执行。先检索全库、生成答案后再遮掉敏感词，已经晚了。

## 回答要能追到具体证据

可以要求模型按下面的约定作答。这是一份应用提示词示例，需要配合引用校验：

```text
根据提供的资料回答问题，不补充资料中没有的具体政策。
每条政策性结论附上对应资料编号，例如 [D2]。
资料不足时明确说缺少什么，不把“未找到”写成“没有这项规定”。
资料之间存在冲突时，列出冲突及版本信息，交由用户确认。
```

服务端应检查 `[D2]` 是否真的存在于这次检索结果中，再映射到原文链接、章节和页码。仅仅出现方括号编号，不等于答案有依据。

也不要把向量相似度当置信度。检索得分很高，只说明在该检索配置下比较接近；仍可能没包含问题真正需要的条件。

## RAGFlow 这类平台怎么用才值

RAGFlow 可以作为搭建知识库应用的一种工具选择。平台帮你组织文档处理与检索，不代表解析质量和答案正确性自动达标。

选择平台时，拿相同文档和问题做对比：表格有没有丢列，权限能否同步，更新后多久生效，检索结果能否单独调试，失败记录能否导出。

不同版本、解析配置和模型会影响结果。学习平台界面之外，还要理解这条数据链路；以后换平台时，这些判断才不会失效。

## 用分层评估找出真正的故障点

| 层次 | 重点检查 |
| --- | --- |
| 解析 | 文字、标题、表格是否正确 |
| 检索 | 前 k 个结果里有没有足够证据 |
| 生成 | 有没有遗漏条件、编造事实或错引资料 |
| 端到端 | 延迟、成本、权限和用户完成率 |

如果证据根本没被检索到，继续微调回答语气意义不大；如果证据齐全却答错，要查上下文组织和生成约束。

第一版先做一个小而干净的知识库，放入包含答案、没有答案、政策冲突和越权查询的样本。把这些情况处理清楚，再扩大文档量。

## 用一个最小项目走完整条链路

第一次动手不需要先处理一百份PDF。先用四条短资料和关键词检索，观察没有证据时如何拒答，再接真实模型。完整过程见[知识助手实战](/articles/knowledge-assistant-project/)。这里先完成纸面练习：写出一个资料能回答的问题、一个资料不足的问题、一个含关键词但缺少关键事实的问题。为三者分别标明应该返回什么。
