控制台里 `await agent.RunAsync()` 很顺。放到 Web 应用后，一个任务跑几分钟，用户关了页面，服务器又正好重启，问题就来了。

异步方法让线程不用一直阻塞，但它不会自动给任务提供持久化、重试和恢复能力。这些仍然需要应用设计。

## 先分清三种“后台”

| 方式 | 谁在继续工作 | 需要你补什么 |
| --- | --- | --- |
| 应用后台任务 | 你的进程或工作进程 | 队列、任务状态、重启恢复 |
| 提供方的 Background Responses | 模型服务 | 继续查询的标识、轮询、取消 |
| 多个后台 Agent | 被委派的子任务 | 并发限制、汇总、失败处理 |

不要把 ASP.NET 请求里随手起一个 `Task.Run` 当作可靠任务队列。请求结束、作用域释放、进程重启，都可能让它留下半截工作。

## 一个可追踪的任务，先有 ID

前端提交任务后，可以先返回业务任务 ID，再通过状态接口或事件流了解进度。任务记录至少区分排队、运行、等待输入、完成、失败和取消。

```text
接收请求 → 校验并保存任务 → 投递队列
工作进程 → 领取任务 → 运行 Agent → 保存结果与状态
前端 → 按任务 ID 查询状态，必要时订阅事件
```

这是架构示意，不是框架自带的完整持久化保证。队列重投、执行超时和重复消费，都要由业务逻辑处理。

同一任务的取消信号也应向下传递到模型与工具，但“请求了取消”不一定表示外部动作已经撤销。界面要以确认后的状态为准。

## 中间件像流水线上的观察点

Agent 中间件可以在运行前后加入日志、校验或策略；模型调用与工具执行也可能有各自的拦截点。把它们看成不同层级，排错会更清楚。

例如，一个 Agent 请求很慢，可能是模型首字延迟高，也可能是连续调用了三个慢工具。只在最外层记录总耗时，无法区分。

流水线顺序也会影响结果。先脱敏再记录，和先记录再脱敏，显然不是同一回事。异常路径、取消路径要经过相应清理，不要只测试成功返回。

## 依赖注入别把会话做成全局共享

通过 DI 注册模型客户端、工具和应用服务，便于配置与测试。但对象能否共享，取决于其线程安全与状态特征。

用户身份、会话和请求内的事务应保持正确作用域。后台任务启动后，不能继续使用已经释放的请求作用域；应由工作进程建立自己的执行作用域，并从持久化记录恢复必要上下文。

## 声明式 Agent 也要版本管理

把模型、指令和工具写进配置，能减少硬编码，但配置也是会改变行为的代码。

可以保存模型部署、提示词版本、工具白名单与预算，并校验不认识的字段。声明式文件的 Schema 必须对应所用运行器，不能把随手写的 YAML 当作框架都能识别的标准。

发布时绑定配置版本，失败时能回滚到确切版本。密钥使用部署环境的凭证机制，不直接放进配置仓库。

## OpenTelemetry 能帮你看到什么

先把一次用户请求、Agent 运行、模型请求和工具调用关联起来，再记录延迟、错误、调用次数及 token 用量。很多问题看完整调用链就能找到原因。

```text
request: ticket-summary-42
  agent.run
    model.call
    tool.get_ticket
    model.call
```

这是预期观察到的层级示意。是否采集到了所有 span，取决于你启用的 instrumentation 与 exporter；装了包，不等于后端已经收到数据。

默认不要记录完整提示词和工具返回值。它们可能包含个人信息或业务秘密。需要排查具体案例时，用可控采样、脱敏和访问限制。

上线验收可以主动让一个工具超时，确认日志里找得到该任务、错误属于哪一步，用户看到的状态也一致。可观察性是帮助定位真实故障，不只是让监控页面出现一条彩色曲线。
