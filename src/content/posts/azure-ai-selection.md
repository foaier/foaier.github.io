第一次打开 Azure 的 AI 产品列表，很容易觉得每个服务都能做相似的事。名字还会变化，旧文章里的 Cognitive Services、Azure AI Foundry，和新文档里的叫法不一定完全一致。

先按职责选，再确认当前产品名称和接口，通常比背一张产品大全更有效。

## 先问：买现成能力，还是自己训练

如果你只是要识别语音、翻译文字、读取发票，先看现成服务。它们已经提供了专门的接口，应用传入内容，接收结构化结果。

如果要用企业数据训练或管理自己的模型，Azure Machine Learning 更相关。它围绕数据、训练作业、实验、模型注册和部署提供能力，不只是一个聊天模型调用入口。

Microsoft Foundry 则围绕模型和 AI 应用开发提供平台能力，涉及模型部署、Agent 和评估等。它可以与其他服务协作，但不能把所有资源的终结点混用。

## 按职责画一张选型表

| 你现在的问题 | 优先了解的能力 | 需要额外确认 |
| --- | --- | --- |
| 音频转文字 | Speech | 语言、噪声、实时或批处理 |
| 发票和表格提取 | Document Intelligence / Content Understanding | 版式、字段、文件限制 |
| 识别图像内容 | Vision 或多模态模型 | 是检测、OCR，还是问答 |
| 给内部文档做搜索 | Azure AI Search 相关能力 | 索引、权限过滤、更新频率 |
| 接入通用模型 | Foundry 的模型部署与推理 | 模型、区域、配额和计费 |
| 训练自己的预测模型 | Azure Machine Learning | 数据版本、训练资源、部署方式 |
| 托管 Agent 与工具 | Foundry Agent 相关服务 | 服务持久化的对象和运行限制 |

截至本文核对时，部分官方页面使用 Foundry Tools、Foundry IQ 等名称。旧路径可能重定向到新页面。**实际开发以资源类型、SDK 和终结点格式为准，不以文章标题里的品牌名为准。**

## 一个文档问答系统，可能需要几个服务

把扫描合同做成知识库，流程可能是：文档解析拿到文本和结构，embedding 模型把文本转成向量，搜索服务保存并检索，语言模型根据检索结果回答。

这些能力之间传递的是数据和调用请求。买了一个模型部署，并不等于自动拥有文档索引；上传了文件，也不意味着它已经完成解析、向量化和权限设置。

可以先手工准备少量干净的文本，跑通检索和回答，再逐步接入扫描件。这样能区分错误究竟出在文档解析、检索还是生成。

## 创建资源前，记下这五项

先记清楚订阅与资源组，避免测试资源散落各处；再选区域，确认所需模型和功能在那里可用；然后看配额和计费单位，不要只看单次调用价格。

身份认证和网络连通性也要提前确认。本地开发可以使用明确的开发者身份，部署后优先考虑合适的托管身份方案。角色分配与网络权限是两回事，拿到了 token 也不代表目标资源一定允许访问。

最后把配置对应起来：资源终结点、项目终结点、部署名和 API 版本。部署名是你创建资源时使用的名字，未必等于模型的原始名字。

## 用最小请求排查，比重装 SDK 快

碰到错误时，先把请求缩到最小：一个短输入，不加工具、不加文件、不接工作流。

- `401` 先查凭证和 token 受众，`403` 查角色、权限与网络限制。
- `404` 查终结点路径、部署名和资源类型是否对应。
- `429` 查配额、并发和重试策略，记录服务返回的等待信息。
- `400` 查响应中的具体错误码，不要把所有参数错误都当成内容过滤。

保留请求 ID 和脱敏后的错误信息，通常比只截一张“调用失败”的图更有帮助。等最小请求稳定，再一项项把功能加回去。
