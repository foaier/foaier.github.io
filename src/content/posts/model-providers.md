很多服务都说兼容 OpenAI API，看起来换模型只需改 `base_url`、密钥和模型名。简单聊天可能确实能跑，但一加工具、视觉或会话状态，就容易出现差异。

兼容的是一组接口约定，不是承诺所有模型、参数和托管工具都一样。

## 先分清 Chat Completions 和 Responses

Chat Completions 以消息列表为核心，应用通常自己组织要发送的上下文。Responses 使用不同的输入输出结构，并可能提供服务端状态、内置工具和后台响应等能力。

不能只把请求路径从一个换成另一个，然后沿用原来的响应解析。流式事件、工具调用结果、继续对话的方法都要按所选 API 处理。

| 要确认的事 | 为什么影响应用 |
| --- | --- |
| 消息由谁保存 | 决定重连后如何恢复会话 |
| 工具调用字段 | 决定参数、调用 ID 与结果如何对应 |
| 结构化输出支持 | 决定能否约束 Schema，以及约束范围 |
| 内置检索或代码工具 | 通常由服务提供，不能随模型任意迁移 |
| 流式完成与错误事件 | 决定前端何时显示完成或失败 |

## Agent Framework 的抽象能帮到哪儿

在 .NET 中，很多应用自管 Agent 建立在 `IChatClient` 抽象之上。它减少了上层应用对某个服务 SDK 的直接依赖。

但抽象不会凭空补出后端没有的能力。一个本地模型能输出文字，不代表它支持可靠的工具调用；接入了同一个 Agent 接口，也不代表它有云端 File Search 或 Code Interpreter。

模型服务提供推理，托管 Agent 服务还可能拥有自己的 Agent 定义、权限和运行状态。这两种接入应分别理解。

## 接 DeepSeek，先核对当前模型目录

截至本文核对时，DeepSeek 官方快速入门列出了 `deepseek-flash` 和 `deepseek-v4-pro` 等模型标识，也说明部分旧名称存在兼容映射。名称与计费会变化，部署时应查看当时的模型说明，不要只依赖旧教程。

第一步用最小文本请求检查连通性，再分别验证工具调用、流式输出和结构化结果。某个扩展字段在原生 API 中可用，不表示 OpenAI 兼容 SDK 会自动保留或正确处理它。

如果确实依赖原生能力，可以把提供方差异限制在适配层，对业务层暴露稳定的输入输出，而不是把特殊字段散落在整个应用。

## 本地 Ollama，先把硬件和模型能力分开

Ollama 帮你在本地运行和调用模型，但真正的表现还取决于模型、量化、上下文长度、显存或内存。

下面是一个最小检查流程。模型名称是示例，需要按本机资源选择；首次拉取会下载模型文件。

```bash
ollama pull qwen3:4b
ollama run qwen3:4b
```

能在终端回答一句话以后，再接应用。接入官方本地 API 时可用 `/api/chat`，响应是否流式由请求配置决定；OpenAI 兼容接口则是另一组路径。不要把原生接口请求体照搬到兼容接口。

本地不等于没有成本：内存、等待时间、并发能力和维护都算成本。桌面演示一个人使用顺畅，不代表服务端十个人同时提问仍然可用。

## 换模型时，重跑这组验收

用相同输入比较：短问答、长文档、缺信息的问题、工具调用、拒绝或错误结果，以及中断的流式响应。

另外检查工具调用 ID 是否成对、结构化字段是否缺失、中文与专有名词表现如何。模型能通过“你好”的测试，只能证明链路基本打通。

先让业务接口保持小而明确，再更换底层模型。这样换供应商是一项可评估的工程工作，而不是一次祈祷。
