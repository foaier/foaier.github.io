“让 AI 看一下这份 PDF。”这句话里，藏着好几种完全不同的任务：识别扫描件里的字、读懂表格、提取发票金额，或者回答整份合同中的某个问题。

如果第一步就选错了处理方式，后面的提示词写得再认真，也很难补救。

## 先把输入拆开看

文字版 PDF 往往能直接提取文字，但阅读顺序未必正确。双栏排版、页眉页脚和跨页表格，都可能把提取结果弄乱。

扫描版 PDF 本质上是一组图片，通常先需要 OCR。OCR 解决“这里写了什么字”，文档结构解析则继续解决“这些字属于哪个标题、单元格和段落”。

| 任务 | 关注点 | 常见误会 |
| --- | --- | --- |
| 图像分类 | 整张图属于哪类 | 不会自动告诉你每个对象的位置 |
| 目标检测 | 找出对象及其位置 | 不等于准确读出所有文字 |
| OCR | 识别文字 | 不保证表格和阅读顺序正确 |
| 文档提取 | 字段、结构和对应关系 | 输出了 JSON 也可能提错值 |
| 多模态问答 | 结合图片和语言理解问题 | 可能猜测图中不清晰的信息 |

例如识别发票时，“合计”可能同时出现在小计、税额和价税合计附近。只拿到几个数字，离正确入账还差一步。

## 文字进来以后，NLP 能做什么

NLP 就是自然语言处理。工单里的实体提取、语言识别、分类、情感分析、摘要和翻译都在这个范围内。

有些任务可以用专用模型或成熟 API，有些可以用通用语言模型。选择依据不是“哪个更智能”，而是准确性、延迟、价格和可验证性。

尤其别把情感分数直接解释为客户真实心理。反讽、行业表达和上下文缺失都会影响结果。业务上更稳妥的做法，是把它当作辅助信号，再结合实际问题分类和人工处理。

语音还要多一道转写：口音、噪声和专有名词都会影响文本。关键号码、金额和姓名需要确认，后续模型无法可靠地修复所有转写错误。

## 提取到字段以后，再加一道校验

假设文档服务返回了下面的数据。这是用于说明校验流程的示例，不对应某家服务的固定响应格式：

```json
{
  "documentId": "invoice-demo-001",
  "amount": "1200.00",
  "currency": "CNY",
  "page": 1,
  "needsReview": false
}
```

接下来至少要检查：金额能否解析、币种是否支持、发票是否重复、明细与合计是否一致。金额运算使用十进制定点类型，避免直接用二进制浮点数做财务计算。

如果识别服务返回置信度，也不要把 `0.95` 理解为这批业务数据上一定有 95% 正确率。应当用自己标注的样本，找出哪些字段、版式和清晰度更容易出错，再设置复核规则。

## 进入知识库时，保留出处

很多文档问答项目的问题不是模型不会答，而是入库时已经丢掉了关键信息。

一段正文应该能追溯到文档、版本、页码和章节。表格切块时保留表头，不能把“金额”列的数字单独切出去；图片相关结论还应保留图片位置，方便人工查看。

文本里的“忽略前面的规则”也只是文档内容，不能自动成为系统指令。把资料和执行权限隔开，后面的 RAG 和 Agent 才有可靠基础。

## 先做一次小规模验收

挑十几份真实版式的样本，覆盖正常、模糊、旋转、空白、跨页表格和缺字段情况。逐项记录提取结果、错误原因和是否需要人工复核。

不要只看演示里最清晰的一张发票。能处理日常那些不太规整的文件，才算走完了从识别到业务的这段路。

## 学完亲手试一次

拿一张没有隐私的测试票据，列出需要提取的字段、允许缺失的字段和必须人工核对的字段。比较“描述图片”与“提取金额”的验收标准，避免把文字流畅当作字段准确。
